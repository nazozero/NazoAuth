## 校准与缺失诊断的具体处理

使用旧 profile.py 的动态起点、小负载和双方共同配置。原公式所需 F 使用**可见规划剩余量**，不再要求能证明所有父级。先跑起来，再观察实际资源与业务结果。

| 遇到的问题 | 必须执行的下一步 |
| --- | --- |
| Docker memory/CPU stats 不可用（如 driver=none） | 尝试任务容器进程的 `/proc` CPU时间及 PSS/smaps_rollup，或可见 cgroup 增量；仍不可得则相应诊断N/A。全局内存增量包含他人负载时，只作压力信号，不冒充k6自身内存。 |
| 无法取得可信的M或sidecar完整迭代P99，旧 formal profile 计算不了 | 不作平方根外推。冻结最后一个双方完成的 pilot 的配置、实际VU和速率，内存字段标 `UNMEASURED_ESTIMATE`，sidecar保持现有已运行配置；作为有界负载A/B继续。不要把估算写为实测。 |
| 只能冻结pilot配置 | profile.stage 改 `formal_bounded_pilot`；保留旧已测试的 main_vu_cap/total_vu_budget/users/vectors。single.start_rate/abba_rate=`max(1,floor(已测试multi速率/N))`，single四sidecar按相同比例缩放速率与VU（均至少1）；multi保留已测试值。双方使用同一配置。此配置不证明容量极限，仍能给出 P99 和稳态。 |
| 内存预检估算本身不适用 | point.py 中仅将可选 `generator_mem_min_gib` 的估算门槛设为0并记录原因；这表示不使用该估算门槛，绝不表示实际内存为0。继续可见内存压力、OOM和超时检查；不得停掉压力监控。 |
| 仅CPU分解、PSS、WAL/成功分母、锁采样等诊断缺失 | 相应指标N/A，其余有效吞吐/P99/审计结果照常交付。统计缺失与零成本明确区分。 |
| 测量stream、完整窗口、源版本、成功/错误分类或审计不变量缺失/失败 | 修复对应工具/采集问题后重试该点；原点保留INVALID/FAIL。不能删这些必要判定，不能称正式验收PASS。其余独立场景继续测。 |
| 发生器 OOM/压力、明确本地资源瓶颈 | 保留失败证据，下调双方共同VU/负载档位，重新运行比较组，仍按实际窗口计量。达到发生器预算时报告下界，不当作NazoAuth极限。 |
| 业务延迟/成功率不达标但测量有效 | 这是FAIL，保留；用较低共同速率找可持续稳态，原失败不能被新PASS覆盖。 |
