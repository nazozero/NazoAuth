## 已确认并修正的测试工具问题

1. **审计组件漏采**：`audit_pair_up` 用 Compose 创建 receiver/worker，它们具有本项目 Compose 标签；进程采样器却只在 `sis.owner` 动态容器集合中找它们。现在通过本项目 Compose 标签解析本点两个精确名字，再复用原 `sample()`。没有扩大到宿主机或其他项目。此修复不能补回历史八个短点已经缺失的资源样本；历史 PARTIAL 仍成立。
2. **冻结用户数与实际种子下限不同**：多核请求写 `user_count=256`、`max_vus=992`，但 `runner.ensure_user_capacity()` 在 seeding 前会将种子用户数提高到至少 992。新的短测请求直接冻结该有效下限，维持本轮实际负载行为，而非削减用户规模取得通过。精确历史种子人数仍应从原生种子文件只提取计数确认，不能发布其中凭据。

sidecar 使用同一份种子文件。其 `user_count=64` 不是独立的 64 人数据库；实际访问集合由 k6 VU 到共享用户表的映射决定。因此“只增加 VU、用户不变”的对照不能只盯请求 JSON：必须固定并记录实际种子数，以及参与访问的用户集合。生产代码和安全锁在这次复核中未作推测性修改。
